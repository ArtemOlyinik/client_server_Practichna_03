## Короткі теоретичні відомості

### 1. Інфраструктура відкритих ключів (PKI) та взаємна автентифікація (mTLS)

У стандартному TLS (односторонньому) тільки клієнт перевіряє автентичність сервера. Сервер надає свій сертифікат, а клієнт перевіряє його дійсність за допомогою списку довірених центрів сертифікації (Root CA).

При **mTLS (Mutual TLS)** сервер і клієнт перевіряють цифрові сертифікати один одного:
1. Клієнт перевіряє сертифікат сервера (захист від атак Man-in-the-Middle).
2. Сервер вимагає та перевіряє клієнтський сертифікат під час TLS-рукостискання (автентифікація клієнта на транспортному рівні без логінів і паролів).

Для тестування mTLS створюється локальний ланцюжок довіри:
- **Root CA:** кореневий сертифікат (`ca.crt`) і закритий ключ (`ca.key`);
- **Сервер:** сертифікат (`server.crt`) і ключ (`server.key`), підписані Root CA;
- **Клієнт:** сертифікат (`client.crt`) і ключ (`client.key`), підписані тим самим Root CA.

Генерація сертифікатів за допомогою утиліти `openssl`:

```bash
# 1. Створення Root CA
openssl req -x509 -newkey rsa:2048 -nodes -keyout ca.key -out ca.crt -days 365 -subj "/CN=MyRootCA"

# 2. Сертифікат сервера (із SAN localhost/127.0.0.1)
openssl req -newkey rsa:2048 -nodes -keyout server.key -out server.csr -subj "/CN=localhost"
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out server.crt -days 365 \
  -extfile <(echo "subjectAltName=DNS:localhost,IP:127.0.0.1")

# 3. Сертифікат клієнта
openssl req -newkey rsa:2048 -nodes -keyout client.key -out client.csr -subj "/CN=dispatcher-agent-01"
openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out client.crt -days 365
```

### 2. Налаштування mTLS у Go (`crypto/tls`)

Пакет `crypto/tls` надає засоби створення як захищених серверів (`tls.Listen`), так і клієнтів (`tls.Dial`).

Ключова конфігурація сервера для виклику mTLS:

```go
// Завантаження сертифіката сервера
cert, err := tls.LoadX509KeyPair("server.crt", "server.key")

// Завантаження довіреного Root CA для перевірки клієнтів
caCert, err := os.ReadFile("ca.crt")
caCertPool := x509.NewCertPool()
caCertPool.AppendCertsFromPEM(caCert)

serverTLSConfig := &tls.Config{
    Certificates: []tls.Certificate{cert},
    ClientAuth:   tls.RequireAndVerifyClientCert, // Обов'язкова вимога клієнтського сертифіката
    ClientCAs:    caCertPool,                     // Довірені CA для клієнтів
    MinVersion:   tls.VersionTLS13,
}

listener, err := tls.Listen("tcp", ":8443", serverTLSConfig)
```

Клієнтська конфігурація для проходження перевірки:

```go
clientCert, err := tls.LoadX509KeyPair("client.crt", "client.key")
caCert, err := os.ReadFile("ca.crt")
caCertPool := x509.NewCertPool()
caCertPool.AppendCertsFromPEM(caCert)

clientTLSConfig := &tls.Config{
    Certificates: []tls.Certificate{clientCert}, // Сертифікат клієнта для сервера
    RootCAs:      caCertPool,                   // Довірені CA для перевірки сервера
}

conn, err := tls.Dial("tcp", "127.0.0.1:8443", clientTLSConfig)
```

### 3. Протокол SMTP та відправка пошти (`net/smtp`)

Протокол SMTP (Simple Mail Transfer Agent) передає текстові команди завершені `\r\n`. Стандартний пакет `net/smtp` містить функцію `smtp.SendMail` для швидкого надсилання листів:

```go
auth := smtp.PlainAuth("", "user@example.com", "password", "smtp.example.com")
// Для локальних емуляторів без авторизації (Mailpit/MailHog) параметр auth передається як nil

to := []string{"admin@example.com"}
msg := []byte("Subject: Тестове сповіщення\r\n\r\nТекст листа")

err := smtp.SendMail("localhost:1025", nil, "server@example.com", to, msg)
```

---

### 4. Формат повідомлень MIME: HTML та вкладення (Attachments)

Стандарт RFC 2045 (MIME) описує структуру електронних листів із підтримкою форматованого тексту та бінарних вкладень:
- Заголовок `Content-Type: multipart/mixed; boundary=...` розділяє повідомлення на логічні частини довільним унікальним текстовим розділювачем (`boundary`).
- Тіло кожної секції починається з власних MIME-заголовків (`Content-Type: text/html; charset=UTF-8`, `Content-Disposition: attachment; filename=...`) та відокремлюється порожнім рядком `\r\n\r\n`.
- Бінарні файли чи звіти кодуються в текстовий формат **Base64** за допомогою пакета `encoding/base64`.

## Постановка задачі

У корпоративних розподілених мережах критично важливі сервіси (наприклад, банківські транзакційні шлюзи або сервери моніторингу електропідстанцій) не повинні бути доступними через відкритий інтернет для анонімних користувачів. Згідно з концепцією **Zero Trust**, кожна взаємодія між підсистемами повинна проходити сувору криптографічну взаємну ідентифікацію на транспортному рівні (mTLS).

У разі реєстрації критичного збою підключений оператор або датчик надсилає сигнал тривоги. Шлюз перевіряє правомірність клієнта, фіксує його ідентифікатор із сертифіката та негайно формує детальне сповіщення відповідальній службі через поштовий протокол SMTP.

Необхідно розробити консольний **шлюз критичних сповіщень та аудиту (Secure Alert Gateway)**, що складається з:
1. **mTLS TCP-сервера**, який приймає з'єднання виключно від клієнтів з валідними сертифікатами спільного CA;
2. **mTLS-клієнта**, який передає термінове повідомлення про подію або аварію;
3. **SMTP-сервісу**, який формує структурований поштовий звіт та відправляє його черговому інженеру на локальний тестовий емулятор або реальний поштовий сервер.

## Завдання

Практична робота складається з трьох послідовних рівнів. Кожен наступний рівень базується на попередньому та розширює функціональність розроблюваного рішення.

### Рівень 1. Базовий: Генерація PKI та захищений mTLS-шлюз

1. **Ініціалізація проєкту:**
    - Створити окрему робочу директорію для практичної роботи.
    - Ініціалізувати Go-модуль за допомогою команди `go mod init <назва_модуля>`.
2. **Генерація інфраструктури сертифікатів (PKI):**
    - Створити окрему папку `certs/`.
    - Згенерувати кореневий сертифікат локального центру сертифікації (`ca.crt`, `ca.key`).
    - Згенерувати закритий ключ і сертифікат сервера (`server.key`, `server.crt`), підписані створеним Root CA, вказавши у розширенні SAN адресу `localhost` або `127.0.0.1`.
    - Згенерувати закритий ключ і сертифікат клієнта (`client.key`, `client.crt`), підписані тим самим Root CA, з атрибутом `CN=dispatcher-agent-01`.
    - Зберегти команди генерації у скрипті `generate_certs.sh` (для Linux/macOS) або `generate_certs.bat` / `generate_certs.ps1` (для Windows).
3. **Реалізація mTLS-сервера:**
    - У файлі `server/main.go` створити TCP-сервер на базі пакета `crypto/tls` (порт `:8443`).
    - Налаштувати `tls.Config`: завантажити серверні ключі, завантажити `ca.crt` у `ClientCAs` та встановити політику автентифікації `tls.RequireAndVerifyClientCert`.
    - Реалізувати прийом текстового повідомлення від підключеного клієнта, виведення тексту у консоль сервера та відправку назад підтвердження: `[SERVER]: ALERT RECEIVED AND VERIFIED`.
4. **Створення авторизованого mTLS-клієнта:**
    - У файлі `client/main.go` реалізувати клієнтське підключення через `tls.Dial`.
    - Налаштувати `tls.Config`: підключити клієнтський сертифікат (`client.crt`, `client.key`) та довірений Root CA (`ca.crt`).
    - Надіслати тестове повідомлення про інцидент: `CRITICAL_ERROR: Database connection timeout on node-04`.
5. **Тестування відхилення неавторизованого доступу:**
    - Спробувати підключитися до сервера клієнтом без сертифіката (наприклад, через команду `openssl s_client -connect localhost:8443` без прапорця `-cert` або через утиліту `curl https://localhost:8443 -k`).
    - Переконатися, що сервер розриває з'єднання під час TLS-рукостискання з помилкою відсутності або недійсності сертифіката.

2. Оформити файл `README.md` з описом проєкту, інструкцією запуску та обов'язковими скриншотами роботи програми (включаючи демонстрацію відсутності помилок).
3. Продемонструвати роботу програми викладачеві та захистити результати.
